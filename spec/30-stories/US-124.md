As Amperlane ops, I want every open exception in one queue, with those I must handle before a booking's grace ends
first, so that I always handle the booking that needs me soonest and never have to watch several tools to find
problems.

## Acceptance criteria

Scenario: S1 · happy path · Every exception type in one queue, most urgent first
  Given open exceptions of each type: a failed station hold, an unacknowledged station hold, a full site, a fault, an unplaced booking, an undelivered time-critical message, a status feed down, a fee decision and an open dispute
  When an ops user opens the exception queue
  Then all of them are listed in one queue
  And each shows its type, its site and its booking, where it has one
  And the exceptions ops must handle before a booking's grace ends come first, ordered by that booking's slot start or, for a site-level exception, by the next allocation it affects, earliest first
  And the other exceptions, such as the fee decision and the dispute, follow them, oldest first

Scenario: S2 · happy path · Closing an exception
  Given an open exception in the queue
  When an ops user resolves it with a reason code
  Then it leaves the queue
  And the booking's history shows the action with the ops user, the reason code and the time

Scenario: S3 · failure · The same problem reported twice gives one exception
  Given a CSMS sends the same fault status for an EVSE twice
  When the ops user opens the queue
  Then the queue holds one exception for that fault

Scenario: S4 · failure · Nobody is signed in when the exception is raised
  Given no ops user is signed in when an exception is raised
  When an ops user signs in later
  Then the exception is in the queue at its place in the queue's order

Scenario: S5 · failure · A user who is not Amperlane ops cannot open the queue
  Given a station operator is signed in to the station portal
  When the station operator tries to open the ops exception queue
  Then access is refused

Scenario: S6 · edge case · An exception whose slot has passed stays in the queue
  Given an open exception whose booking's slot start has passed
  When an ops user opens the queue
  Then the exception is still listed until an ops user resolves it

Scenario: S7 · edge case · A feed outage takes the place of the next allocation it affects
  Given an open exception for JFK's status feed being down
  And an open failed station hold for a Gowanus booking whose slot starts before the next JFK allocation runs
  And an open unplaced-booking exception for an LIC booking whose slot starts after the slot of the JFK booking that allocation is for
  And an open dispute on a no-show whose booking ended days ago
  When an ops user opens the queue
  Then the Gowanus exception, the JFK feed exception and the LIC exception are listed in that order
  And the dispute is listed after all three
