# JS-413 · Sign-ins, role changes and production access on record

When the rideshare platform's security team, a SOC 2 auditor or Amperlane itself asks who signed in, who failed to,
who changed a role or permission, who accessed production data or who changed a configuration, I want each of those
events recorded with its actor and time since the first release, so I can answer from the record instead of piecing
it together from memory and chat history.

## Acceptance criteria

Scenario: S1 (happy path) A sign-in and a role change
  Given an ops person signs in to the ops console
  When the ops person changes the role of a station portal user
  Then the sign-in and the role change are each recorded with the actor and the time

Scenario: S2 (failure) Repeated failed sign-ins
  Given a fleet portal account
  When someone fails to sign in to it several times
  Then each failed attempt is recorded with the account and the time
  And no password or one-time code that was entered is recorded

Scenario: S3 (failure) Production data accessed outside the application
  Given an engineer with a production role
  When the engineer queries production data from a database console instead of through the platform
  Then the access is recorded with the engineer and the time

Scenario: S4 (edge case) A configuration change
  Given an ops person changes the grace period configured for LIC
  When the change is saved
  Then the configuration change is recorded with the ops person and the time

Scenario: S5 (edge case) The record starts with the first release
  Given the first production release has been deployed
  When a sign-in happens on the day of that release
  Then it is on record with its actor and time

Scenario: S6 (failure) Someone tries to remove a security event
  Given a recorded role change
  When any user, including the person who made the change, tries to edit or delete that record
  Then the attempt is refused
  And the record is unchanged

## Notes

- The rideshare platform asked for SOC 2 Type I and a pen test (SRC-C2@00:43:30); Amperlane owns the audit
  (CTX-107). Before and after values of role and configuration changes are REQ-262 (JS-414). Constitution SC5 applies
  (no secrets in logs).
- Whether drivers opening a signed link or entering a one-time code (REQ-240, REQ-241) count as sign-ins for this
  requirement is a design detail for Step 3.3.
- Red team: a log the actor can clean up afterwards answers nobody; S6 applies the audit trail's append-only rule
  (constitution N17 test: the application role cannot update or delete audit rows), as JS-414 S3 and JS-415 S4 do.
