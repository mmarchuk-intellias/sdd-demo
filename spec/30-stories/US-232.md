# US-232 · Gowanus charger reservations sent and cancelled through AMPECO

As Amperlane ops, I want charger reservations for Gowanus bookings sent and cancelled through Kinship's AMPECO API,
so that a booked EVSE at Gowanus is held at the charger without anyone in ops phoning Kinship, and released again when
the booking no longer needs it.

## Acceptance criteria

Scenario: S1 (happy path) A charger reservation is sent through AMPECO
  Given a Gowanus booking is allocated to an EVSE flagged as reservable
  When the platform places the charger reservation for that booking (timing and expiry: REQ-024)
  Then a reservation request for that EVSE, with that expiry, is sent through the AMPECO API
  And AMPECO's acceptance is recorded against the booking with its time

Scenario: S2 (happy path) A charger reservation is cancelled through AMPECO
  Given a Gowanus booking has a charger reservation that AMPECO accepted
  When the booking is cancelled
  Then a cancellation request for that charger reservation is sent through the AMPECO API
  And AMPECO's answer to the cancellation is recorded against the booking with its time

Scenario: S3 (failure) AMPECO rejects the charger reservation
  Given a Gowanus booking is allocated to an EVSE flagged as reservable
  And the charger of that EVSE rejects charger reservations
  When the reservation request is sent through the AMPECO API
  Then the charger reservation is recorded against the booking as rejected, with its time
  And the booking stays confirmed (REQ-023)

Scenario: S4 (failure) AMPECO does not answer the reservation request
  Given the AMPECO API does not answer
  When a reservation request for a Gowanus booking is sent
  Then the charger reservation is recorded against the booking as not answered, with its time
  And the booking stays confirmed (REQ-023)

Scenario: S5 (failure) AMPECO does not answer the cancellation
  Given a Gowanus booking with a charger reservation that AMPECO accepted is cancelled
  And the AMPECO API does not answer the cancellation request
  When the cancellation request is sent
  Then the cancellation is recorded against the booking as not answered, with its time
  And the booking stays cancelled

Scenario: S6 (edge case) An EVSE that is not reservable
  Given a Gowanus booking is allocated to an EVSE not flagged as reservable
  When the site's station-hold offset before the slot is reached
  Then no reservation request is sent through the AMPECO API for that EVSE

## Notes

- Split from US-201 by the red team (P3.2, INVEST): reservations depend on Q-009 (sandbox access, the firmware fix,
  which chargers accept charger reservations); status reading does not. A-022 sets the March baseline.
  integrations.md U-1: charger reservations work on 10 of 16 Gowanus chargers; the reservable flag is REQ-025.
- This story covers only what crosses the AMPECO API. When the reservation is sent and its expiry are REQ-024 (US-021);
  which booking changes cancel a reservation is REQ-153 (US-027); the fallback after a rejected or unanswered
  reservation (signage request, ops exception) is REQ-155 and REQ-023 (JS-023); running Gowanus as a status-only site
  during an AMPECO outage is REQ-167 (JS-024).
- Whether an unanswered cancellation (S5) is retried is a design detail for Step 3.3; a reservation left at the
  charger keeps the EVSE from walk-ups until it expires (CTX-066).
