# US-412 · Booking history with actor and reason code that nobody can edit

As an Amperlane ops person, I want every booking state change, override, manual ops action and station hold recorded
with who did it (the system or a named person), a specific reason code from a fixed catalogue and the time, in a trail
that nobody can edit or delete, so that I can answer a driver, a fleet or a station operator about any booking from
evidence, and a booking rebooked after a charger fault never shows as a no-show.

## Acceptance criteria

Scenario: S1 (happy path) The system rebooks after a charger fault
  Given a confirmed booking at Gowanus whose allocated EVSE has a charger fault
  When the platform rebooks it to another EVSE
  Then the booking's history shows the change with the system as actor, the reason code for a charger-fault rebook and the time
  And the booking is not shown as a no-show anywhere

Scenario: S2 (happy path) Ops overrides a booking
  Given a booking in grace at JFK
  When an ops person force-releases it with a reason code from the catalogue
  Then the booking's history shows the release with that ops person as actor, the reason code and the time

Scenario: S3 (failure) An override with a reason that is not in the catalogue
  Given an ops person forcing a booking's state
  When the ops person submits the override with a free-text reason, or with a code that is not in the catalogue
  Then the override is refused
  And the booking's state is unchanged

Scenario: S4 (failure) Someone tries to change the history
  Given a recorded entry in a booking's history
  When any user, ops or engineer, tries to edit or delete it, through the platform or with the database access the
    platform itself uses
  Then the attempt is refused
  And a correction can only be added as a new entry that refers to the earlier one

Scenario: S5 (edge case) Every change the system makes on its own has a specific code
  Given the state changes the platform makes without a person (hold expiry, allocation, auto-release, rebooking after a fault)
  When each of them happens to a booking
  Then each is recorded with the system as actor and a reason code that names that change
  And no two of these changes share a reason code
  And none is recorded with a catch-all code such as "other" or "system update"

Scenario: S6 (edge case) A station hold that the charger rejects
  Given a booking allocated at Gowanus to an EVSE whose charger rejects the charger reservation
  When the station hold is attempted
  Then the booking's history shows the attempt, its rejection, the system as actor and the time

Scenario: S7 (happy path) A manual ops action that is not an override
  Given an ops person places a maintenance hold on an EVSE at JFK that has a confirmed booking
  When the hold is saved and the booking is rebooked because of it
  Then the audit trail shows the hold with the ops person as actor, its reason code and the time
  And the booking's history shows the rebooking with its own reason code and the time

## Notes

- "If I move a booking, it should say 'moved — charger fault', not 'no-show'" (SRC-C2@00:53:32); "All in the audit
  log" (SRC-C2@00:53:46). Constitution N17 (append-only, enforced in the database) and SC6 apply.
- Payouts are in the trail only where the business model has them (Q-001); no payout scenario until then.
- The dispute screen that reads this history is REQ-179 (EP-03); changes to configuration with before and after
  values are JS-414; who viewed a driver's data is JS-415.
- Red team: S3 refuses a free-text reason (a "fixed catalogue", REQ-053); an override with no reason at all is US-128
  S4. S4 names the database access the platform uses, because a rule enforced only in the user interface passes a
  test through the platform (constitution N17). S5 makes "specific" testable: a single code such as "system" for every
  automatic change is generic. S7 covers manual ops actions other than overrides (REQ-126). S6 asserts the audit
  entry; the per-booking station-hold record that ops read in a dispute is US-028. A maintenance hold reassigns
  bookings as on a fault (A-018).
