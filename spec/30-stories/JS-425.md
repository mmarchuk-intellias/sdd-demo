# JS-425 · A repeated save of a capacity-rule change applies once

When I save a change to a site's capacity rule and the portal or console seems not to respond, I want to save it
again without risk, so I can tell that my change was saved once, without an error caused by my own first save and
without two entries in the change history.

## Acceptance criteria

Scenario: S1 (happy path) A new capacity rule saved twice
  Given a Kinship Charging user adds a Saturday capacity rule at Gowanus in the station portal
  And the response does not reach the browser
  When the user saves the same rule again from the same form
  Then the second request carries the same idempotency key as the first
  And the site has the rule once
  And the second response shows the rule as saved, not as overlapping the rule the first save created
  And the change history shows one change (JS-414)

Scenario: S2 (failure) The same key with a different change
  Given a capacity-rule change saved with an idempotency key
  When a change with a different cap arrives with the same idempotency key
  Then the request is rejected as a reused key
  And the capacity rule is unchanged

Scenario: S3 (failure) A refused change is repeated
  Given a capacity-rule change that was refused because it overlaps another rule of the site (US-311 S3)
  When the same request is repeated with the same idempotency key
  Then the response is the same refusal
  And the site's capacity rules are unchanged

Scenario: S4 (edge case) Two deliberate changes, each with its own key
  Given a station operator lowers a cap, and later the same day lowers the same cap again from a fresh form
  When both changes arrive
  Then both are applied
  And the change history shows two changes, each with its own before and after values

Scenario: S5 (edge case) Ops saves a change for a station operator twice
  Given an ops person changes the capacity rule at JFK on behalf of Jamaica Bay Energy
  And the response does not reach the ops console
  When the ops person saves it again from the same form
  Then the rule changes once
  And the change history shows one change, with the ops person as actor

## Notes

- Split from JS-421 at the Step 3.1 red team: REQ-236 names capacity-rule changes among the commands that carry an
  idempotency key, and JS-421 is the driver's situation. A retried ops override is US-128 S5 and a retried ops booking
  US-127 S6 (both REQ-236).
- Station operators change caps themselves (CTX-065). Capacity rules are US-311 (REQ-077); the change history is
  JS-414 (REQ-262). How long keys are kept, and rejecting a reused key with a different request: A-035. Constitution
  N8 and code conventions row 8 apply.
- S4 checks that repeats are recognised by their key, not by who sent what within a short time.
