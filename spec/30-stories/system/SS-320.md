# SS-320 · Signed driver links: bound to the first device, driver-scoped, with expiry and renewal

As the Identity & access component, I need every link in a driver message to be signed, bound to the device that first
opens it, limited to that driver's bookings and valid until a set time after the booking's grace ends, so that a driver
reaches a booking in one tap without a password while a leaked link reaches nothing.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Identity & access component shall issue each link in a message about a booking as a signed token
   bound to one driver number and that booking, which opens without a password.
2. [Event] When a link is opened for the first time, the Identity & access component shall bind it to that device and
   open a driver session for that driver, with the full or the limited scope of SS-321.
3. [Event] When a link is opened again on the device it is bound to before it expires, the Identity & access component
   shall open the driver session again without a password.
4. [Ubiquitous] The Identity & access component shall expire a booking's link the configured link validity after the
   end of that booking's grace period, grace extensions included.
5. [Unwanted] If a link is opened on a device other than the one it is bound to, then the Identity & access component
   shall open no session, return no booking or personal data, and return how to get a new link by texting from the
   registered number.
6. [Unwanted] If a link's signature does not verify, then the Identity & access component shall open no session and
   return no booking or personal data.
7. [Unwanted] If a link is opened after it expired, then the Identity & access component shall open no session, return
   no booking, and return how to get a new link by texting from the registered number.
8. [Ubiquitous] The Identity & access component shall limit a driver session to bookings whose booker or charging
   driver is the session's number and refuse every request about another booking.
9. [Event] When a link request arrives from a registered number (SS-310), the Identity & access component shall issue a
   new link to that number's driver page, valid from its issue for the configured link validity for a driver-page link
   requested by text, to be sent to that number only.
10. [Unwanted] If a link request comes from a number registered to no fleet, then the Identity & access component shall
    issue no link.
11. [Ubiquitous] The Identity & access component shall apply the number's current entitlement (SS-319) to every action
    of a driver session, so a link issued before a removal books nothing for that fleet.
12. [Ubiquitous] The Identity & access component shall keep link tokens out of logs, traces and error responses
    (constitution SC5).

## Notes
- Depends on A-006 (signed links, no password) and Q-028. "Single-use" in REQ-240 is read as one device per link
  (clauses 2 and 5); a link forwarded before the driver opens it is JS-221 (SS-321).
- What the driver texts for a new link is the "link" keyword of SS-310 (#27). The first opening of a link on a device is
  logged as a sign-in (#47, SS-334).
- The page that opens, a cancelled booking's page included, is the Driver PWA (SS-325, US-211 S1, S4, S5).
- Baseline: constitution N15 (drivers use signed links), SC3, SC5.
- P3.4 (2026-10-28): clause 1 bound every link to one booking, which contradicted clause 9's driver-page link; it now
  covers links in messages about a booking. Clause 9 names its own parameter as in SS-026 clause 2 (link validity for a
  driver-page link requested by text, counted from issue), distinct from clause 4's link validity after grace.
