# SS-432 · Versioned, documented API used by every front-end

As the Platform & operations component (API gateway), I need every booking function that the driver PWA, portals,
attendant view and ops console use to be offered through one versioned, documented API that those front-ends use
themselves, so that the platform is API-first as the brief asks.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Platform & operations component shall expose every booking function that the driver PWA, fleet
   portal, station portal, attendant view and ops console use through the platform API, under an explicit version,
   with each endpoint described in a machine-readable description published with that version.
2. [Unwanted] If a front-end reaches a booking function other than through the published API, then the Platform &
   operations component shall fail the pipeline run.
3. [Unwanted] If a change alters a published API version so that it no longer matches its published description, then
   the Platform & operations component shall fail the pipeline run unless the change is released as a new version.
4. [Unwanted] If an endpoint has no description of its request, response and error codes, then the Platform &
   operations component shall fail the pipeline run.
5. [State] While a front-end still calls an earlier API version, the Platform & operations component shall keep
   serving that version.

## Notes
- Enabler: REQ-139 has no story. "API-first" is in the brief (SRC-D1#9).
- The error model (problem details with stable codes) is constitution code convention 7; idempotency headers are code
  convention 8 and SS-014. An API for external partners (OCPI and others) is not in scope here (I and V items).
- design.md §2.2 lists the API gateway as proposed; the ss-plan places it in Platform & operations (§5.2, item 7).
