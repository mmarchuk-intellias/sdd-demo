# SS-342 · Sensitive-identifier register: listed, encrypted, named roles, reads audited; unlisted not stored

As the Audit & data protection component, I need every credential and licence or account number the platform holds to
be listed, encrypted, readable only by named roles and audited on every read, and no such number to be stored without
an approved purpose, so that SHIELD-covered data stays as small and as protected as possible.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Audit & data protection component shall list in the data register every credential and every
   licence or account number field the platform holds, each with the purpose Amperlane approved and the roles allowed
   to read it.
2. [Ubiquitous] The Audit & data protection component shall keep each listed field encrypted at rest (constitution
   N14).
3. [Event] When a listed field is read, the Audit & data protection component shall append an audit entry with the
   reader, the field, the record and the time.
4. [Unwanted] If a role not named for a listed field asks to read it, then the Audit & data protection component shall
   refuse it and record a security event (SS-334).
5. [Unwanted] If an input or a data import would store a driver's licence number, TLC licence number or bank account
   number without a register entry that records an approved purpose for it, then the Audit & data protection component
   shall refuse to store it.

## Notes
- Enabler: REQ-253 and REQ-265 have no story. No K or Y requirement needs licence or account numbers today; payment
  cards stay at the payment provider (SS-414). Staff passwords stay with the identity provider (constitution N15);
  integration secrets in the managed secret store (N14).
- The SHIELD marking used in a breach scope comes from this register (SS-338). Retention periods: Q-022.
