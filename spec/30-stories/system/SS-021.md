# SS-021 · Site time zones, instants and daylight-saving changes

As the Booking engine, I need to keep every booking time as an instant and lay out each site's slots in the site's own
time zone, so that drivers arrive at the right local time across daylight-saving changes and a site in another metro
needs no change to the booking core.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Booking engine shall store every hold, booking and slot time as an instant, and lay out each
   site's time grid, bookable hours and capacity-rule windows in the site's configured time zone.
2. [Ubiquitous] The Booking engine shall return every booking time as an instant together with the site's local date
   and time and the zone abbreviation, whatever time zone the requester is in.
3. [Ubiquitous] The Booking engine shall end every booking exactly its booked duration after its start in elapsed
   time, including a booking that spans a daylight-saving change.
4. [Event] When a requested local start time occurs twice at the site because of the autumn daylight-saving change, the
   Booking engine shall record one instant, the occurrence the request names, or the next occurrence when it names
   none, and return it with the zone abbreviation that tells the two apart.
5. [Unwanted] If a requested local start time does not exist at the site because of the spring daylight-saving change,
   then the Booking engine shall refuse it with the code OFF_GRID and offer no start time in that gap.
6. [Ubiquitous] The Booking engine shall lay out the slots and booking times of a site configured in a time zone other
   than America/New_York in that site's zone, with the same booking-core code that runs the NYC sites.

## Notes
- Covers US-016 S1 – S4 (the PWA display is SS-329), US-014 S4 (clause 6; onboarding is SS-028), JS-008 S4 and
  US-306 S5 (each booking with its own date in the site's zone; the fleet portal view is SS-223).
- A-013 (per-site time zone, times as instants); code conventions row 10. The daylight-saving changes happen at night,
  so clauses 4 and 5 rely on overnight bookings (REQ-152, A-028; CF-015 needs-decision).
- Timer instants are computed from these instants (SS-032). A text time is read in the site's zone (SS-022).
- P3.4 (2026-10-28): clause 6 was an [Event] whose trigger was a test run ("booked, allocated and released on the
  release that runs the NYC sites", with "release" meaning both a software release and a booking release); it is now
  the [Ubiquitous] property that REQ-138's end-to-end test checks.
