# SS-421 · Open pilot bookings carried over at cut-over, drivers told

As the Pilot migration & cut-over component, I need every pilot booking for a slot at or after the cut-over instant to
exist in the platform as a confirmed booking that runs like any other, and its driver to be told how to manage it, so
that ops honour every booking promised in the pilot without opening Airtable or the Sheets.

## Acceptance criteria (EARS)
1. [Event] When the cut-over runs (SS-422), the Pilot migration & cut-over component shall request the Booking engine
   to record, for each pilot booking whose slot starts at or after the cut-over instant, a confirmed booking with its
   driver, fleet, site and window, the vehicle the fleet named for it during the cut-over preparation or else the one
   vehicle the fleet has registered for that driver (A-061), the site's booking parameters and partner terms in force at
   the cut-over instant, and the reason code CARRIED_OVER_AT_CUTOVER (SS-020), linked to its pilot source record.
2. [Unwanted] If a pilot booking's slot started before the cut-over instant, then the Pilot migration & cut-over
   component shall not carry it over, also when the slot ends after the instant, so that the Amperlane Concierge
   finishes it.
3. [Event] When a driver's bookings have been carried over, the Pilot migration & cut-over component shall report them
   to Messaging for that driver's cut-over message (SS-306).
4. [Unwanted] If the driver's mobile number is registered to no fleet in the platform, then the Pilot migration &
   cut-over component shall still carry the booking over (clause 1) and list it in the cut-over result for ops with the
   reason "driver not registered".
5. [Unwanted] If Messaging reports a carried-over booking as "driver not told", then the Pilot migration & cut-over
   component shall list it in the cut-over result for ops with that reason.
6. [Ubiquitous] The Pilot migration & cut-over component shall carry each booking over with the window the pilot
   promised, also when that window is not one of the site's configured booking durations.
7. [Unwanted] If carried-over bookings for one slot exceed the cap of the site's capacity rule, then the Pilot
   migration & cut-over component shall carry every one of them over, drop or rebook none, and list them in the cut-over
   result for ops as above the site's cap.
8. [Unwanted] If the carry-over is run again, for example after a failure part-way, then the Pilot migration & cut-over
   component shall request no second booking for a pilot booking already carried over and report no booking to
   Messaging a second time.
9. [Event] When the carry-over finishes, the Pilot migration & cut-over component shall publish the cut-over result for
   ops with the number of bookings carried over and each listed booking with its reason.
10. [Event] When a carried-over booking has been recorded, the Pilot migration & cut-over component shall request the
    Booking workflows component to start that booking's workflow with its timers (SS-032), so that it is allocated and
    given its station hold like a booking made in the platform.
11. [Unwanted] If a migrated copy of a carried-over pilot booking exists (SS-416), then the Pilot migration & cut-over
    component shall replace it with the carried-over booking, so that the platform holds the source record once
    (SS-417 clause 7).
12. [Unwanted] If the fleet named no vehicle for a pilot booking and does not have exactly one vehicle registered for
    its driver, then the Pilot migration & cut-over component shall still carry it over (clause 1) without a vehicle, as
    REQ-231 v2 requires, and list it in the cut-over result for ops with the reason "vehicle not registered", so that ops
    set its vehicle with a reason code before its allocation offset (A-061).
