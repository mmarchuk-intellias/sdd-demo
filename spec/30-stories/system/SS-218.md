# SS-218 · CSMS webhook signature or shared-secret verification

As the CSMS integrations, I need to verify every inbound CSMS webhook before acting on it and reject and log the ones
that do not verify, so that nobody can change EVSE status or bookings by posting to a webhook endpoint.

## Acceptance criteria (EARS)
1. [Event] When a CSMS webhook arrives, the CSMS integration shall verify its signature or shared secret before it
   parses the content.
2. [Unwanted] If a CSMS webhook's signature or shared secret is missing or does not verify, then the CSMS integration
   shall reject it with an authentication error, change no state, and log the rejection with the integration, the
   source address and the time, without the payload.
3. [Optional] Where a CSMS does not sign its webhooks, the CSMS integration shall require a per-integration shared
   secret, configured with the vendor, on every webhook it accepts.
4. [Ubiquitous] The CSMS integrations shall read webhook secrets only from the managed secret store, so that a secret
   can be replaced without a code change.

## Notes
- Enabler: REQ-260 has no story (ss-plan §4.2). The messaging-provider side is SS-317.
- A rejected webhook loses no status: the reconciliation poll still runs (SS-201, constitution N9).
- Basis: constitution SC3 (webhook signatures verified where the provider signs), SC5 (no payload in logs), N14
  (secrets only in a managed store).
- Whether AMPECO and ChargeLab sign their webhooks, or accept a configured shared secret, is not known: Q-061 (1),
  with Q-009 and Q-012. With neither, status comes from polling only (SS-201, constitution N9).
