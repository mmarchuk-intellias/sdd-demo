# SS-007 · Burst fairness with per-site decisions in received order

As the Booking engine, I need to decide competing requests for capacity at a site in the order the platform received
them and answer every request that loses, so that at the shift-change burst an earlier driver never loses a slot to a
later one and nobody is left without an answer.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Booking engine shall decide hold and confirmation requests for capacity at one site in the order in
   which they reached the platform edge, whatever channel each came through, even when a later request could be
   processed sooner.
2. [Unwanted] If more requests arrive for a slot than it has capacity left, then the Booking engine shall answer every
   request that loses with a same-site offer (SS-009) or an explicit SLOT_FULL answer, and never with a server error or
   no answer.
3. [Ubiquitous] The Booking engine shall grant requests for different slots that each have room, whatever order they
   were received in.
4. [Event] When several requests that lost the same slot get same-site offers, the Booking engine shall make the offers
   in the order the requests were received, so an earlier loser is offered the earlier free slot and a later loser the
   next free slot after it, or SLOT_FULL.
5. [Ubiquitous] The Booking engine shall not make a request for one site wait behind requests for another site.

## Notes
- Covers JS-010 S1, S3 – S5 and JS-004 S5. JS-010 S2 and S6 are SS-008.
- ADR-006 (single-writer order per site, losers get an alternative instead of an error); A-009 (the burst is
  concentrated on a few sites); A-034 (every loser gets an alternative or an explicit "full").
- "Reached the platform edge" is the instant A-032 starts measuring from; a text booking reaches it when the inbound
  SMS is accepted (SS-309, SS-311).
