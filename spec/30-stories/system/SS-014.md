# SS-014 · Idempotent booking commands with original result and key reuse refused

As the Booking engine, I need every state-changing booking command to carry an idempotency key and a repeat of it to
return the first result, so that a driver who taps twice on bad 4G, or a retried ops request, gets exactly one booking
and one answer.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Booking engine shall require an idempotency key on every state-changing command of the booking
   API (hold, confirm, cancel, running late, accept or decline an offer, ops booking, ops override, manual hold) and
   refuse a command without one with the code IDEMPOTENCY_KEY_REQUIRED.
2. [Event] When a command arrives with a key already stored for the same request, the Booking engine shall return the
   stored result of the first request and make no further state change, for at least the 7 days of A-035.
3. [Unwanted] If a command arrives with a stored key and a different request, then the Booking engine shall refuse it
   with the code IDEMPOTENCY_KEY_REUSED (HTTP 409) and change no booking, hold or offer.
4. [Ubiquitous] The Booking engine shall look up the idempotency key before any hold, capacity or state check, so a
   repeated confirm that arrives after the hold's time to confirm returns the booking the first confirm made.
5. [Unwanted] If a second request with a key arrives while the first request with that key is still being processed,
   then the Booking engine shall return the first request's result to both and process the command once.
6. [Ubiquitous] The Booking engine shall emit each booking event once per state change, so a repeated command causes
   no second confirmation, cancellation or offer message.
