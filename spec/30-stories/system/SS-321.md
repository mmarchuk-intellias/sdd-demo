# SS-321 · Limited view and one-time codes on unverified devices, with lockout

As the Identity & access component, I need a device that has not recently completed a one-time code for the driver to
reach only the booking's site, time and one-tap actions, and everything else to need a code sent to the registered
number, so that a forwarded link lets the next shift act on the booking in one tap without exposing the driver's data.

## Acceptance criteria (EARS)
1. [State] While a device has not completed a one-time code for the link's driver within the configured verified-device
   period, the Identity & access component shall give its session the limited scope: the booking's site and start time
   and its one-tap actions only.
2. [Event] When a limited session sends one of the booking's one-tap actions (cancel, running late, accept an offered
   slot or alternative, report a faulted EVSE, report a blocked stall), the Identity & access component shall
   authorise it without a code.
3. [Unwanted] If a limited session asks for any other data or change, the open-slot view, a hold and a booking
   included, then the Identity & access component shall refuse it until a valid code is entered on that device.
4. [Event] When a limited session asks for more than the limited scope, the Identity & access component shall request
   Messaging to send a one-time code by SMS to the registered number of the link's driver (SS-304), valid for the
   configured one-time-code validity.
5. [Event] When a valid, unexpired code is entered on the device, the Identity & access component shall mark the device
   as verified for that driver for the configured verified-device period and give its session the driver's full scope.
6. [Unwanted] If a wrong or expired code is entered, then the Identity & access component shall keep the limited scope
   and change nothing.
7. [Unwanted] If the configured wrong-code limit for codes in a row is reached for a driver number, then the Identity &
   access component shall refuse every code for that number for the configured code lockout time.
8. [State] While a device is verified for the driver, the Identity & access component shall open the driver's links on
   it with full scope and ask for no code.
9. [Ubiquitous] The Identity & access component shall ask for the code before the open-slot view is shown, not at
   confirmation.
10. [State] While codes for a driver number are refused under clause 7, the Identity & access component shall show ops
    the block with the number and the time it ends.

## Notes
- Settles bucket-5 item #26: the code is asked before the open-slot view; the two taps of REQ-100 and N23 count from
  the open-slot view, so a first booking on a new phone is the code plus two taps (US-212 S7; PWA side SS-326).
- Settles bucket-5 item #37: after a configured number of wrong codes, codes for that number are refused for a
  configured time, and ops can see the block (clause 7). Defaults for the four values are in design.md §8 (A-059).
- REQ-241 v2 (CR-001): no one-tap action needs the code (clause 2). Accepted risk: the holder of a forwarded link can
  act on that booking in those ways.
- Depends on A-006 and Q-028. The code SMS passes the agreement gate of SS-304; whether a code the driver asks for
  needs a recorded agreement is a NEW-Q in the log (extends Q-056). Code entries are logged as sign-ins (#47, SS-334).
- P3.4 (2026-10-28): clause 4 sends the code through Messaging, so the agreement gate of SS-304 applies and clause 4 no
  longer contradicts SS-304 clause 1 for a number with no agreement (open question in ss-log-4, NEW-Q 1). Old clause 7
  split into clauses 7 and 10.
- P3.4: parameter names aligned with SS-026 clause 2 (verified-device period, one-time-code validity, wrong-code limit,
  code lockout time).
