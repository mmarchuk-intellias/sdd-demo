# SS-413 · Payment webhooks with scheduled status reconciliation

As the Payments integration (Stripe), I need to turn every payment webhook into one status update for its invoice,
whatever duplicates or order the provider sends, and to reconcile every open invoice with the provider on a schedule, so
that an invoice's payment status matches the provider's and is never wrong for longer than one payment check interval.

## Acceptance criteria (EARS)
1. [Event] When a payment webhook whose signature verifies arrives, the Payments integration shall report to the Ledger
   & invoicing component (SS-409) the current state of the invoice it names, as read from the provider (paid with its
   payment time, payment attempt failed, or open).
2. [Unwanted] If a webhook's signature does not verify, then the Payments integration shall reject it, log the
   rejection and change nothing.
3. [Unwanted] If a webhook with an event id already processed arrives again, then the Payments integration shall not
   apply it a second time.
4. [Unwanted] If payment webhooks arrive out of order, then the Payments integration shall leave the invoice in the
   state the provider holds, the same final state as in-order delivery.
5. [Event] When the configured payment check interval elapses, the Payments integration shall read from the provider the
   status of every issued invoice not yet paid and report each change that no webhook delivered.
6. [Unwanted] If the provider is unavailable at a scheduled check, then the Payments integration shall keep each
   invoice's last reported status with its time and run the check again at the next interval.
7. [Event] When the platform returns from its maintenance window, the Payments integration shall apply every payment
   the provider took during the window, from the provider's retried webhooks or the next scheduled check.

## Notes
- Covers JS-322 S3 (clause 5), S4 (3, 4); US-323 S1 and S4 (clause 1 feeds SS-409); US-321 S1 ("shown as paid once
  Stripe reports", clause 1), S2 (the failed attempt, clause 1), S4 (clause 7).
- P3.4 critique: clause 1 held three behaviours (verify, read, report); verification failure is clause 2, and
  clause 1 now starts from a verified webhook.
- US-321 is added as a parent (batch-5 log): its status scenarios reuse these clauses instead of repeating them in
  SS-414.
- Contract (ss-plan §5.1): payment-webhook idempotency lives here; CSMS webhooks are SS-200, messaging SS-307.
  Signature verification follows constitution SC3 (REQ-260 names CSMS and messaging webhooks only; GAP-5-2 in the log).
- Reading the invoice's current state on each webhook (clause 1) makes the final state independent of order (N9).
- The payment check interval is the platform parameter of REQ-110 in SS-026's catalogue (default in design.md §8, A-059).
  While the provider itself is down, clause 6 can leave a status older than one interval; nothing can be paid at the
  provider then.
- The payout part of REQ-110 applies only if Q-001 brings payouts (REQ-278 parked).
