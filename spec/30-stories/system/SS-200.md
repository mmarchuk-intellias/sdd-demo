# SS-200 · Status event application: idempotent, ordered by observed-at, source recorded

As the EVSE status service, I need to apply every normalised status event exactly once and in the order the status was
observed, keeping its source, so that duplicated or late webhooks never change an EVSE's status twice or roll it back,
and status age can be measured the same way at every site.

## Acceptance criteria (EARS)
1. [Event] When the EVSE status service receives a status event for an EVSE whose observed-at time is later than that
   of the status it holds for that EVSE, the EVSE status service shall hold the event's status as the EVSE's current
   status, with that observed-at time and the event's source (CSMS webhook, CSMS poll or attendant).
2. [Event] When the current status of an EVSE changes to a different value, the EVSE status service shall emit exactly
   one status-changed event with the EVSE, the previous and the new status, the observed-at time and the source.
3. [Unwanted] If a status event arrives whose observed-at time is earlier than that of the status held for the EVSE,
   then the EVSE status service shall keep the held status as current and emit no status-changed event for it.
4. [Unwanted] If a status event arrives that the EVSE status service has already applied (same provider event id, or
   for an event without one the same EVSE, status, source and observed-at time), then the EVSE status service shall
   change no status and emit no event for it.
5. [Ubiquitous] The EVSE status service shall leave every EVSE in the same current status after any duplicated or
   reordered delivery of a set of status events as after in-order delivery of that set.
6. [Ubiquitous] The EVSE status service shall measure each EVSE's status age as the time since it last received or
   fetched a status for that EVSE from the site's status source, whether or not the status changed (A-031).

## Notes
- Covers JS-206 S1 and S3, US-201 S1 and S3, US-203 S1, JS-116 S4 and S5 (no status change, so no fault event, SS-208).
- Inputs are normalised by the CSMS integrations (SS-211, SS-214) and the attendant view (SS-207); validation and
  mapping happen there (constitution SC7). Idempotency of CSMS status webhooks is owned here (ss-plan §5.1); the
  mechanics follow constitution N8, N9 and code convention 8; key retention A-035.
- Observed-at: the CSMS's timestamp for a webhook; the time of the fetch for a poll result (US-203 S2).
- The 60-second bound itself is SS-201 (REQ-104, REQ-107); staleness on reads is SS-202; history is SS-205.
- Depends on A-031 (how age is measured), Q-009 and Q-012 (AMPECO polling and the ChargeLab feed are unconfirmed,
  integrations.md U-8).
