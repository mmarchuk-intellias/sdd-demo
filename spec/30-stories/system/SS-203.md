# SS-203 · Status feed outage: bookings continue, status stale, ops exception before the next allocation

As the EVSE status service, I need to detect when a connected site's status feed is down, raise one ops exception for
it before the site's next allocation, and change no booking because of the outage, so that bookings go on within the
capacity rules while ops know the site's status cannot be vouched for.

## Acceptance criteria (EARS)
1. [Event] When every EVSE at a connected site has a status age above 60 seconds, the EVSE status service shall mark the
   site's status feed as unavailable.
2. [Unwanted] If an allocation at a connected site requests EVSE status while every EVSE of the site has a status age
   above 60 seconds and no status-feed-down exception is open for the site, then the EVSE status service shall raise
   that exception before it answers the request.
3. [Unwanted] If the feed of a site already marked unavailable stays down, then the EVSE status service shall raise no
   further status-feed-down exception for the same outage.
4. [State] While a connected site's status feed is unavailable, the EVSE status service shall emit no event that makes
   the booking engine refuse, cancel, release or rebook a booking at the site, so bookings there are accepted or
   refused by the capacity rules alone.
5. [Event] When a connected site whose feed is marked unavailable delivers a status again, the EVSE status service
   shall clear the mark and emit a feed-recovered event naming the site and the time.
6. [Event] When the EVSE status service marks a connected site's status feed as unavailable, the EVSE status service
   shall raise one ops exception of type "status feed down" naming the site and the time a status was last received from
   it.

## Notes
- Covers JS-210 S1, S2, S4 and S6 (with SS-204 for the silence rule), JS-206 S4 (with SS-201 and SS-202), US-124's
  status-feed-down type, US-201 S2 and US-203 S3 (no booking changed; the next status replaces the stale one through
  SS-200), US-207 S3 (with SS-202).
- "Unavailable" uses the stale threshold of REQ-160 (60 seconds, constitution N2) for every EVSE of the site, so no
  separate detection time is configured; with the proposed poll interval it means about three missed polls and no
  webhook. It relies on the reconciliation poll (SS-201): at a site whose CSMS offers no status poll, a quiet period
  with no status change would read as an outage (Q-009, Q-012).
- This SS raises the status-feed-down exception (ss-plan §5.1); its place in the queue (by the next allocation it
  affects) and its closing by ops with a reason code are SS-219. The feed-recovered event is shown on the open
  exception; ops still close it (US-124 S2).
- How allocation uses each EVSE's last known status during the outage is SS-101 (batch 2); Gowanus station holds
  during an AMPECO outage are SS-122. LIC has no feed (attendant view), so this SS does not apply there.
- Depends on Q-012 (JFK feed), Q-023 (who acts at night), A-031 (an outage is not a freshness breach).
- P3.4 (2026-10-28): old clause 1 (mark the feed unavailable and raise the exception) split into clauses 1 and 6;
  "unavailable" is still defined by clause 1.
