# SS-025 · Idempotent capacity-rule changes with one change and one history entry per key

As the Inventory & site configuration module, I need every capacity-rule change to carry an idempotency key and a
repeat of it to return the first result, so that a station operator or ops person who saves twice gets one change, one
history entry and no error caused by their own first save.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Inventory & site configuration module shall require an idempotency key on every capacity-rule
   change from the station portal or the ops console and refuse a change without one with the code
   IDEMPOTENCY_KEY_REQUIRED.
2. [Event] When a capacity-rule change arrives with a key already stored for the same request, the Inventory & site
   configuration module shall return the stored result of the first request, the saved rule or the original refusal,
   and make no change and no new change-history entry.
3. [Unwanted] If a capacity-rule change arrives with a stored key and a different request, then the Inventory & site
   configuration module shall refuse it with the code IDEMPOTENCY_KEY_REUSED (HTTP 409) and leave the rule unchanged.
4. [Ubiquitous] The Inventory & site configuration module shall look up the idempotency key before validating a change,
   so a repeat of a saved rule is answered as saved and not as overlapping the rule the first save created.
5. [Event] When two capacity-rule changes with different keys arrive, the Inventory & site configuration module shall
   apply each and record a change-history entry for each, with its own actor and before and after values.
