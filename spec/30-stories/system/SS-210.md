# SS-210 · Driver fault report: ops alert linked to site and EVSE, never a status

As the EVSE status service, I need to turn a driver's report of a faulted EVSE into one ops exception linked to the
site, the EVSE and the booking, without changing the EVSE's status, so that ops can act on what drivers see while
status still comes only from the site's own source.

## Acceptance criteria (EARS)
1. [Event] When a driver reports the allocated EVSE of the driver's booking as faulted, from the booking page or by
   message, the EVSE status service shall raise one ops exception of type "driver fault report" linked to the site,
   the EVSE and the booking, with the time of the report.
2. [Ubiquitous] The EVSE status service shall include in each driver-fault-report exception the EVSE's current status
   with its observed-at time and source.
3. [Unwanted] If the same driver report is received again (the same idempotency key or provider message id), then the
   EVSE status service shall keep a single exception for it.
4. [Unwanted] If the reporting driver's booking has no allocated EVSE yet, then the EVSE status service shall raise the
   exception linked to the site and the booking, marked as EVSE not identified.
5. [Ubiquitous] The EVSE status service shall not change an EVSE's live status, exclude it from allocation or start
   fault rebooking because of a driver report.

## Notes
- Covers JS-117 S1, S2, S4 and S5, and US-208 S4. JS-117 S3 (a message the platform cannot understand) is SS-312.
- The one-tap action is SS-327 (no one-time code needed, REQ-241 v2); the keyword is SS-310. Idempotency follows
  constitution N8 and code convention 8; this SS states it only for the exception (JS-117 S4).
- The exception type is raised here (ss-plan §5.1); queue and closing are SS-219. Automatic fault rebooking starts only
  from a CSMS or attendant fault (SS-208); ops can rebook all bookings of the EVSE in one action (SS-112).
