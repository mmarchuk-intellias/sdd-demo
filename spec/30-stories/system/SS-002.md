# SS-002 · Hold placement on the time grid with configured durations, cap check and hold time

As the Booking engine, I need to place a hold on one unit of capacity only when every slot it covers stays within its
capacity rule's cap, and let the hold lapse at the site's hold time, so that the cap agreed with the station operator
is never exceeded and unconfirmed capacity returns to other bookers.

## Acceptance criteria (EARS)
1. [Event] When a hold request names a site, a start time on the site's time grid, one of the site's configured booking
   durations and a vehicle the booker may book, and every slot the booking would cover stays within the cap of its
   capacity rule with the new hold counted, the Booking engine shall place a hold on one unit of capacity for that
   site, window and vehicle that expires at the site's configured hold time after it was placed.
2. [Unwanted] If the start time is not on the site's time grid, then the Booking engine shall refuse the request with
   the code OFF_GRID and place no hold.
3. [Unwanted] If the holds and bookings overlapping any slot the booking would cover already equal the cap of the
   capacity rule for that slot, then the Booking engine shall refuse the hold with the code SLOT_FULL, leave the count
   in every slot unchanged and request a same-site offer (SS-009).
4. [Ubiquitous] The Booking engine shall count every unexpired hold and every confirmed booking that overlaps a slot
   against the cap of that slot's capacity rule.
5. [Ubiquitous] The Booking engine shall check each slot a booking covers against the capacity rule in force for that
   slot, so a booking that spans the windows of two rules is accepted only if it stays within each rule's cap.
6. [Ubiquitous] The Booking engine shall stop counting a hold against any cap from its expiry instant, whether or not
   its hold-expiry timer has fired yet.
7. [Event] When the hold-expiry timer fires for a hold that was not confirmed (SS-032), the Booking engine shall record
   the hold as expired, with the system as actor and the reason code 'hold expired'.
8. [Unwanted] If a booker's confirmation arrives for a hold that has expired, then the Booking engine shall refuse it
   with the code HOLD_EXPIRED and create no booking, unless SS-014 returns the result of an earlier request with the
   same idempotency key; an ops force-confirm of an expired hold follows SS-016 clause 1 instead.
9. [Unwanted] If a hold request names a site that the Inventory & site configuration module reports as not bookable
   (SS-028), then the Booking engine shall refuse it with the code SITE_NOT_BOOKABLE and place no hold.
10. [Ubiquitous] The Booking engine shall apply the same hold, cap and expiry rules at sites of every supply pattern,
    so the same request against the same site configuration gets the same result and reason code at Gowanus, JFK and
    LIC.
11. [Unwanted] If the duration is not one of the site's configured booking durations, then the Booking engine shall
    refuse the request with the code DURATION_NOT_OFFERED and place no hold.

  names the booker's confirmation, so it no longer contradicts the ops force-confirm of an expired hold (SS-016).

  driver is shown is SS-326); US-127 S5; US-205 S1 (clause 10, REQ-028). US-002 S3 is SS-023.
- Depends on A-001 (grid, durations and hold time are configured values, SS-026), A-005 (holds are database rows).
- Clause 6 keeps a late timer during planned downtime (constitution N5) from holding capacity beyond the hold time.
- Out-of-hours requests are refused under SS-001; compatibility under SS-004; parties under SS-005 and SS-006; order
  at burst time under SS-007. Every SS-002 refusal code is a typed result (code conventions row 7).
