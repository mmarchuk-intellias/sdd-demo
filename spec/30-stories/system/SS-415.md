# SS-415 · Payment-provider interface: provider replaceable without core changes

As the Payments integration (Stripe), I need to sit behind a payment-provider interface written in the platform's own
terms, so that Stripe can be replaced without changing the booking core or the ledger.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Payments integration shall offer the core one payment-provider interface in the platform's own
   terms (submit an invoice, read an invoice's status, receive payment events, get a payment page link), with no
   provider type in it.
2. [Ubiquitous] The Payments integration shall be the only module that imports the Stripe SDK or a Stripe type.
3. [Unwanted] If the provider returns an error, then the Payments integration shall translate it into one of the
   interface's own error codes (PROVIDER_UNAVAILABLE, SUBMISSION_REJECTED, IDEMPOTENCY_CONFLICT) and pass no provider
   error type to the core.
4. [Optional] Where a second implementation of the payment-provider interface is configured in place of Stripe, the
   Payments integration shall pass the core's invoicing contract tests with no change to the ledger or the booking
   core.

## Notes
- Enabler: REQ-111 has no story. A-007 (Stripe stays the provider, behind an interface); ADR-003 and ADR-011 (Adyen for
  Platforms named as an alternative "only for pricing at scale", SRC-C2@00:47:10).
- Clause 2 is checked by the import lint of constitution code convention 5.
- The second implementation of clause 4 is a test double; no second provider is integrated in v1.
- P3.4 critique: clause 4 was labelled [Event] with a configuration choice as its trigger; it is the [Optional]
  pattern. Clause 2 is a code-structure rule kept because REQ-111 is one; it is tested by the import lint.
