# SS-317 · Messaging webhook signature verification

As the Messaging component, I need to accept inbound messaging webhooks only when the provider's signature verifies, so
that nobody can book, cancel or fake a delivery report by posting to the webhook.

## Acceptance criteria (EARS)
1. [Event] When an inbound-message or delivery-report webhook arrives, the Messaging component shall verify the
   messaging provider's signature over the request with the configured provider secret before reading the request
   further.
2. [Unwanted] If the signature is missing or does not verify, then the Messaging component shall reject the request
   without processing it, replying to anyone or changing any state.
3. [Unwanted] If the signature is missing or does not verify, then the Messaging component shall log the rejection as a
   security event (SS-334) with the endpoint, the source address and the time, and without the message body
   (constitution SC5).
4. [Ubiquitous] The Messaging component shall verify the signature before deduplication (SS-309), so that a rejected
   request never marks a provider message id as processed.

## Notes
- Enabler: REQ-260 has no story. The CSMS side of REQ-260 is SS-218.
- Twilio signs its webhooks (A-008); the secret lives in the managed secret store (constitution N14). Constitution SC3
  (webhook signatures verified where the provider signs) and SC7 (schema validation at the edge) apply.
