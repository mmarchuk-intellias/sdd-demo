# SS-103 · Database exclusion constraint rejects overlapping active allocations from any writer

As the Allocation & rebooking component, I need my database to reject any overlapping active allocation on one EVSE, so
that the no-double-booking rule holds even when application code is wrong.

## Acceptance criteria (EARS)
1. [Ubiquitous] The Allocation & rebooking component shall store each allocation with its EVSE, its time range (SS-102)
   and whether it is active, under a PostgreSQL exclusion constraint that rejects any insert or update leaving two
   active allocations on one EVSE with overlapping time ranges.
2. [Unwanted] If a write made directly with the application's database role, bypassing the Allocation & rebooking
   component's code, would create an overlapping active allocation, then the Allocation & rebooking component shall
   reject the write through that constraint.
3. [Unwanted] If two concurrent transactions each try to create an active allocation on the same EVSE with overlapping
   time ranges, then the Allocation & rebooking component shall commit exactly one of them through that constraint.
4. [Event] When an allocation is deactivated, the Allocation & rebooking component shall accept a new active allocation
   on that EVSE whose time range overlaps the deactivated one.
5. [Unwanted] If the constraint rejects an allocation write, then the Allocation & rebooking component shall return a
   stable domain code for a taken EVSE to its caller and never a 5xx fault.

## Notes
- ADR-006 (the SQL there is an illustration, not the schema); constitution N7 (integration test on real PostgreSQL, load
  test with zero overlaps, daily production query with an alert) and code conventions 7 (a constraint violation maps to
  its domain code), 10 and 13.
- Enabler: REQ-101 has no story; US-011 (SS-102) states the application behaviour.
- CF-023: the constraint can bite only at allocation (ADR-005); before it, the pool check of SS-003 protects capacity
  (A-014).
