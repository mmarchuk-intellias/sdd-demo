# SS-300 · Booking confirmation and cancellation messages: one per booking per recipient

As the Messaging component, I need to send the charging driver, and a booker with a registered number, exactly one
confirmation per booking made in the platform that states what was booked and on which terms, and the same recipients
one cancellation message when the booking is cancelled or released by ops, so that drivers know where they stand
without calling ops and never mistake two messages for two bookings.

## Acceptance criteria (EARS)
1. [Event] When the booking engine reports a booking as confirmed that was not carried over at cut-over (clause 13),
   the Messaging component shall send the booking's charging driver one confirmation for it.
2. [Ubiquitous] The Messaging component shall state in every confirmation the site, the date and the start time in the
   site's time zone with the zone indicated, the duration, the vehicle and the booking code.
3. [Ubiquitous] The Messaging component shall state in every confirmation the grace period and the no-show fee terms
   fixed for the booking at confirmation (SS-027), the site's cancellation cut-off included, with a fee recorded as zero
   stated as "no fee".
4. [Ubiquitous] The Messaging component shall write each confirmation in its own recipient's language (SS-303), so a
   booker and a charging driver with different languages each get it in their own.
5. [Event] When one confirmation step confirms more than one booking, the Messaging component shall send each
   recipient one confirmation per booking, each with its own date, start time, booking code and link.
6. [Unwanted] If the confirmation of a booking is requested again, through a retried confirmation step, a repeated
   request with the same idempotency key or a duplicate inbound message, then the Messaging component shall send no
   further confirmation for that booking to either recipient.
7. [Event] When the Messaging component resumes after planned downtime with confirmations still due, the Messaging
   component shall send each due confirmation once, late if need be (constitution N5).
8. [Event] When the booking engine reports a booking as confirmed that was not carried over at cut-over (clause 13)
   and whose booker is a registered number other than the charging driver, the Messaging component shall send the
   booker one confirmation for it.
9. [Unwanted] If a confirmed booking's booker is a fleet-portal or ops user rather than a registered number, then the
   Messaging component shall send the booker no confirmation.
10. [Event] When the booking engine reports a booking cancelled (SS-013), an ops force-release included (SS-016), the
    Messaging component shall send the booking's charging driver, and a booker with a registered number other than the
    charging driver, each one cancellation message in their own language naming the booking by its code, site and
    start time.
11. [Unwanted] If a booking was cancelled by a cancel keyword from its charging driver's or its booker's number, then
    the Messaging component shall send the reply of SS-310 clause 7 as that number's cancellation message and no second
    one to it.
12. [Unwanted] If the cancellation or release of a booking is reported to the Messaging component more than once,
    through a repeated command with the same idempotency key or a retried force-release, then the Messaging component
    shall send no further cancellation message for it.
13. [Unwanted] If a booking reported as confirmed was carried over at cut-over (reason code CARRIED_OVER_AT_CUTOVER,
    SS-003 clause 9), then the Messaging component shall send no confirmation for it to any recipient, so that the
    cut-over message (SS-306 clause 6) is the driver's one message about it.
