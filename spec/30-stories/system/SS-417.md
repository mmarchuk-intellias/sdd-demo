# SS-417 · Re-runnable migration with per-record outcome and count reconciliation

As the Pilot migration & cut-over component, I need a migration that can be re-run, gives every source booking record
exactly one outcome, loaded or rejected with a reason, and reconciles its counts with the export files, so that Amperlane
can prove no pilot booking was lost and fix a mapping problem by re-running instead of patching data by hand.

## Acceptance criteria (EARS)
1. [Event] When a migration run processes a source booking record, the Pilot migration & cut-over component shall give
   it exactly one outcome: loaded, alone or merged with its counterpart under the precedence rule (SS-419), or rejected
   with a reason.
2. [Unwanted] If a record carries a status value that no mapping rule covers, then the Pilot migration & cut-over
   component shall reject it with the reason "unknown status value" and go on with the other records.
3. [Unwanted] If a row of an export file cannot be read, such as a row with a broken date or a missing column, then the
   Pilot migration & cut-over component shall reject it with the reason "unreadable record" and its file and row
   position, and count it.
4. [Ubiquitous] The Pilot migration & cut-over component shall count each record under its source, its site, its
   original status and the month of its slot start in the site's time zone, counting a value it cannot read as
   "unknown".
5. [Event] When a run finishes, the Pilot migration & cut-over component shall compare, for every source, month, site
   and original status, loaded plus rejected records with the count taken from the export files, and mark the run
   complete only if every count matches.
6. [Unwanted] If any count differs, then the Pilot migration & cut-over component shall report the run as failed,
   naming each source, month, site and original status whose counts differ, and shall not mark it complete.
7. [Event] When the migration is run again on the same export, the Pilot migration & cut-over component shall hold each
   source record at most once in the platform, keyed by its source system and source id, replacing its earlier
   migrated copy rather than adding another.
8. [Unwanted] If a re-run meets a booking made in the platform, or a pilot booking carried over at cut-over (SS-421),
   then the Pilot migration & cut-over component shall leave that booking, and everything the platform has recorded
   for it, unchanged.

## Notes
- Covers US-401 S1 (clauses 1, 4, 5), S2 (2), S3 (6), S4 (7), S5 (8), S6 (3, 4).
- Settles bucket-5 #49: a record's month, and the 2026-02-01 boundary of SS-418, are taken from the booking's slot
  start in the site's time zone, as US-327 does.
- The counts are taken from the export files themselves, unreadable rows included, not from the loader's own reader
  (US-401 red team); counting per source avoids counting a booking held in both Airtable and a Sheet twice.
- A carried-over booking's source record counts as loaded (it is the carried-over booking, SS-421).
- Depends on Q-020 (scope and cleansing) and A-026; the raw export Priya Nair promised (SRC-C2@00:58:37) is SS-420.
