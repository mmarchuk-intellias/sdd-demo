# SS-214 · ChargeLab status by webhook or poll, with payload validation

As the ChargeLab integration (CSMS integrations), I need to turn JFK status from the ChargeLab API, pushed or polled,
into normalised status events and reject anything I cannot validate or map, so that the EVSE status service has valid
JFK status at the site where status is the only live signal.

## Acceptance criteria (EARS)
1. [Optional] Where ChargeLab sends status changes by webhook, the ChargeLab integration shall pass the EVSE status
   service a normalised status event for each, with the EVSE, the mapped platform status, ChargeLab's timestamp as
   observed-at, the source "ChargeLab webhook" and ChargeLab's event id.
2. [Event] When the EVSE status service requests a reconciliation poll of JFK, the ChargeLab integration shall fetch the
   status of every JFK EVSE from the ChargeLab API and pass each as a normalised status event with the time of the
   fetch as observed-at and the source "ChargeLab poll".
3. [Ubiquitous] The ChargeLab integration shall map each ChargeLab status value to exactly one platform status
   (available, occupied, charging, faulted or unknown).
4. [Unwanted] If a ChargeLab response or webhook fails schema validation, carries a status value with no mapping, or
   names an EVSE not mapped to a JFK EVSE, then the ChargeLab integration shall reject it, pass nothing to the EVSE
   status service, and record the rejection with its reason.
5. [Unwanted] If the ChargeLab API does not answer a reconciliation poll, then the ChargeLab integration shall report the
   poll to the EVSE status service as failed and pass no status.
6. [Ubiquitous] The ChargeLab integration shall declare no charger-reservation capability on the CSMS interface
   (SS-217), so no charger reservation is ever sent to ChargeLab.
