# US-410 · Production access by role for named people, logged from the first release

As the Amperlane CTO, I want access to production systems and data granted only through roles to people I can name,
and every access logged from the first release, so that I can show the rideshare platform's security team and a SOC 2
auditor who can reach production and what they did there, without having to rebuild access control later.

## Acceptance criteria

Scenario: S1 (happy path) A named engineer with a production role
  Given an Amperlane engineer named in a production support role
  When the engineer reads production booking data
  Then access is granted
  And the access log shows the person, the role used, what was accessed and when

Scenario: S2 (failure) A person with no production role
  Given an Intellias developer who holds no production role
  When the developer tries to reach a production system
  Then access is refused
  And the refused attempt is in the access log with the person and the time

Scenario: S3 (failure) A role that does not cover the action
  Given an Amperlane ops person whose role covers the ops console only
  When the ops person tries to query the production database directly
  Then access is refused
  And the refused attempt is in the access log

Scenario: S4 (edge case) Automated access by the deployment pipeline
  Given the deployment pipeline changes production
  When the change is applied
  Then it acts under its own named identity with a role and a named owner
  And the access is logged like a person's

Scenario: S5 (edge case) Logging starts with the first release
  Given the first production release has been deployed
  When the Amperlane CTO asks for production access since that release
  Then every access since that release is in the access log, starting with the release itself

Scenario: S6 (failure) A shared account
  Given a staff account that several people use, or that is not tied to one named person
  When anyone tries to give that account a production role
  Then the role is not granted
  And the account cannot reach a production system

## Notes

- "I don't want to find out in a year we need to rewrite auth" (SRC-C2@00:44:25). Working assumption A-038; the
  constitution N15 baseline (single sign-on with MFA, quarterly review, removal on leaving) applies and is not
  restated here.
- Security events in detail (sign-ins, failed sign-ins, role changes, configuration changes) are JS-413 (REQ-121).
- Red team: a shared "ops" login holding a production role passes S1 (the log shows "a person", but not who); S6
  closes it, since REQ-120 limits access to named people. How the access log is protected from the people whose
  access it records is a design detail for Step 3.3.
  What portal users may see is US-411 (REQ-258).
