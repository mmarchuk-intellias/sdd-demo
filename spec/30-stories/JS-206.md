# JS-206 · EVSE status no older than 60 seconds, even when a webhook is lost

When a driver is a few minutes from a connected site at the shift change, I want to rely on EVSE status that is no
more than 60 seconds old, even if a status webhook was lost, so I can tell whether an EVSE is really free before the
driver gets there.

## Acceptance criteria

Scenario: S1 (happy path) A status change arrives by webhook
  Given a connected site (Gowanus or JFK) whose CSMS sends status changes by webhook
  When an EVSE's status changes and the webhook arrives
  Then the platform holds the new status
  And the EVSE's status age, measured as A-031 defines, is at most 60 seconds

Scenario: S2 (failure) A webhook is lost
  Given a connected site whose CSMS sends status changes by webhook
  And the webhook for an EVSE's status change never arrives
  When the periodic poll of that site runs
  Then the platform holds the changed status, taken from the poll, no later than 60 seconds after the CSMS reported
    the change
  And the EVSE's status age, measured as A-031 defines, stays at most 60 seconds

Scenario: S3 (failure) A late webhook carries an older status
  Given the poll has returned an EVSE's newer status
  When a webhook with an older observation time arrives afterwards
  Then the platform keeps the newer status
  And the status age is counted from the latest time the platform received or fetched the EVSE's status

Scenario: S4 (failure) The station operator's API is unreachable
  Given the CSMS API of a connected site does not answer
  When an EVSE's status age passes 60 seconds
  Then the status is shown as stale with its age
  And the minutes in which the API is unreachable are not counted as breaches of the 60-second target (A-031)

Scenario: S5 (edge case) The status does not change for a long time
  Given an EVSE at a connected site stays free for an hour
  When the platform keeps receiving or fetching its unchanged status
  Then the EVSE's status age stays at most 60 seconds throughout the hour

Scenario: S6 (edge case) The target over a month
  Given a calendar month of the availability window (constitution N4)
  When status age per EVSE is evaluated for that month
  Then each EVSE at a connected site has a status age of at most 60 seconds in at least 99% of the minutes in which
    its station operator's API is reachable (A-031)

## Notes

- "I" is Amperlane ops, and the platform acting for them at the pre-arrival check.
- Connected sites today are Gowanus (AMPECO) and JFK (ChargeLab); LIC has no API and shows attendant status (US-207).
- Depends on A-031 (how age is measured, CSMS outages) and Q-012: push or poll and 60-second freshness at JFK are
  unconfirmed (integrations.md U-8). Polling AMPECO for status is not confirmed either: AMPECO is confirmed for status
  webhooks and REST (integrations.md I-1); Q-009 covers sandbox access to check it.
- Baseline: constitution N1, N9, N21 (alert at 60 s). Duplicate and out-of-order webhooks in general are REQ-106
  (FT-14.3).
