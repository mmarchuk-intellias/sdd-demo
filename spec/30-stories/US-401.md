# US-401 · Re-runnable pilot migration that reconciles with the export

As the Amperlane engineer who supplies the pilot exports (Priya Nair), I want a pilot migration I can re-run that
loads every source booking record or lists it as rejected with a reason, and whose counts by month, site and original
status equal those of the source export, so that I can prove no pilot booking was lost and fix a mapping problem by
re-running the migration instead of patching data by hand.

## Acceptance criteria

Scenario: S1 (happy path) Every source record is accounted for
  Given a raw export from Airtable and the pilot Google Sheets whose booking records per source, month, site and
    original status have been counted from the export files themselves
  When the migration runs
  Then every source booking record is either loaded (alone, or merged with its counterpart in the other source by the
    precedence rule of US-403) or on the rejected list with a reason
  And for every source, month, site and original status, loaded plus rejected records equal the count taken from the
    export files

Scenario: S2 (failure) A record cannot be mapped
  Given a source booking record with a status value that no mapping rule covers
  When the migration runs
  Then that record is on the rejected list with the reason "unknown status value"
  And the run continues with the other records
  And the counts by month, site and original status still reconcile

Scenario: S3 (failure) The counts do not reconcile
  Given a run in which a source record ends up neither loaded nor rejected
  When the migration finishes
  Then the run is reported as failed, naming each month, site and original status whose counts differ
  And the run is not marked complete

Scenario: S4 (edge case) Re-run after a mapping rule is fixed
  Given a completed run with records rejected for an unknown status value
  And the mapping rule for that value has since been added
  When the migration is run again on the same export
  Then those records are loaded
  And no source record appears twice in the platform
  And the counts reconcile again

Scenario: S5 (edge case) Re-run after launch
  Given bookings have been made in the platform since launch
  And pilot bookings carried over at cut-over (JS-407) have since been allocated, cancelled or completed in the platform
  When the migration is run again
  Then no booking made in the platform is changed or removed
  And no carried-over booking loses or changes what the platform has recorded for it since the cut-over

Scenario: S6 (failure) A source row that cannot be read
  Given an export file with a row that cannot be read, such as a row with a broken date or a missing column
  When the migration runs
  Then that row is on the rejected list with the reason "unreadable record" and its position in the file
  And it is counted, so the counts by source, month, site and original status still reconcile

## Notes

- Depends on Q-020 (scope, how much cleansing) and the raw export Priya Nair promised (SRC-C2@00:58:37); A-026.
- "Original status" is the status as recorded in the source, before re-classification (US-402).
- Red team: counts can reconcile while records are attached to the wrong driver or site; US-400 S1 and S5 cover
  linking. Counts taken by the migration's own reader would reconcile even if it skipped rows it could not parse; S1
  counts from the export files and S6 makes an unreadable row a rejection, not a silent skip. Counting per source
  avoids double counting a booking held in both Airtable and a Sheet.
- Month is the month of the booking's slot start in the site's time zone (a design detail for Step 3.3, as in US-327).
